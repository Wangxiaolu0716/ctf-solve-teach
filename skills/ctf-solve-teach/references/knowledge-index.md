## FMT · 文件格式与容器

| ID | 知识点 | 一句话原理 | 典型征兆 |
|---|---|---|---|
| FMT-01 | Magic number | 文件类型由头部字节决定，扩展名只是给资源管理器看的 | 后缀和 `file` 结果不一致 |
| FMT-02 | 容器嵌套 | 一个文件可以在任意偏移处完整包含另一个文件 | 尾部熵突变、carve 出多个结果 |
| FMT-03 | 长度字段自校验 | 格式里"长度/尺寸"和实际数据量必须互相吻合，改一个就会撕裂 | PNG 解码失败、CRC 错 |
| FMT-04 | 尾部附加数据 | 很多格式允许在结束标记后追加任意字节，解析器会忽略 | JPEG 有 EOI 但后面还有数据 |
| FMT-05 | 元数据字段 | EXIF/tEXt/docProps 是格式允许的"自由文本框"，出题人最爱 | 图片能开但 EXIF 有一长串奇怪字符串 |
| FMT-06 | 结构偏移 | 改一个字节会连带它后面的所有偏移失效（如 ZIP 目录偏移） | 能列出条目但解压报错 |
| FMT-07 | 变长整数（vint） | RAR5/Protobuf 用"高位续读"编码整数，算偏移时漏掉字段自身字节就全盘错位 | 解析出的类型/长度是 35、42958046 这类非法值 |
| FMT-08 | 结束标记后的自由区 | PNG `IEND`、JPEG `FFD9`、PDF `%%EOF`、GIF `0x3B` 之后都不被解析，是天然的藏数据区 | 图片能开，但文件比"该有的长度"长 |

## 深水区（值得讲 5 分钟的部分）

### FMT-03 · PNG 的长度自校验为什么能反推宽高

PNG 的像素数据在 IDAT 块里，采用 zlib 压缩。解压后的字节数必须满足
`行字节数 = 1 + 宽 × 每像素字节数`（第一个字节是过滤器类型），再乘高。
所以拿到 `IDAT 总长度` 和 `每像素字节数`，可以解一个二元一次方程反推 (宽,高)。
出题人改 IHDR 的宽高却不改数据，解码器就会读到越界或提前结束 → 报错或显示不全。
**识别**：CRC 错、解码失败、画面下半部分被裁掉。
**注意**：真彩/索引色/16 位深的每像素字节数不同，先看 IHDR 的 bit depth 和 color type。

### FMT-06 / ZIP 的三个陷阱

1. **伪加密**：只改通用位标志的 bit0，数据其实没加密。修回去即可。
2. **bit3 数据描述符**：加密标志在本地头里被置位时，CRC 和大小被移到数据后面，
   于是字典爆破常用的"校验字节"（12 字节）失效 → 改用已知明文前缀（`--magic`）。
3. **局部头与中央目录不一致**：两个地方都记了文件名/大小/偏移，出题人改一处就会出现
   "能列出但解不出"。这时要同时看两处（`ctf zip --no-auto` 会都打出来）。

### CRY-03 · RSA 小指数为什么要开方而不是解密

`c = m^e mod n`。若 `m^e < n`，取模根本没发生，`c` 就是 `m^e` 本身，
于是 `m = c^(1/e)`（整数开方）。判断条件：`e` 很小（3/5/17）且 `c` 的比特数
明显小于 `n` 的比特数。变体：给多组同 m 的密文 → 低指数广播（CRT 合并后再开方）。

### FRN-03 · USB 键盘流量为什么是 8 字节

USB HID 键盘的输入报告固定 8 字节：修饰键、保留、6 个同时按下的键码。
所以一帧能表示"最多 6 个键同按"，字符还原要查 HID Usage Table（`0x04=a` …）。
**坑**：`00` 表示无按键（不是空格）；shift 由修饰键字节表示；
有的题目做了自定义映射表，这时要看有没有附带 json/py。

### STG-01 · LSB 为什么必须"按位平面"看而不是"按像素"看

最低位对亮度贡献 1/256，人眼不可见。单个像素的 LSB 是噪声，但把所有像素的
同一 bit 抽出来拼成一张二值图，信息就浮现了。这就是 stegsolve 的位平面视图。
**变体**：只改 R 通道、按列扫描、先异或再取位、LSB 里再套一层编码。
**验证**：命中后要能重复提取出稳定字符串，否则是噪声巧合。

### FMT-08 · 怎么算"这个文件本该多大"

任何自描述格式都声明了"我该在哪结束"，解析器读到这里就 return，后面的字节
既不解析也不报错。所以判断尾部有没有藏东西，就是做一次减法：

```text
PNG  : IEND 类型字段位置 + 8（4 字节类型 + 4 字节 CRC）
JPEG : 最后一个 FFD9
GIF  : 最后一个 0x3B
PDF  : 最后一个 %%EOF
差值 = 文件实际大小 − 结束偏移
差值 > 0 → 尾部有附加数据
```

`ctf info` 会直接把差值打出来（"逻辑结尾=… 实际大小=… 尾部多余 N 字节"）。
**坑**：① "图能打开"不能证明没藏东西；② 某些 binwalk 版本对 PNG 尾附只报 offset
不自动拆；③ 尾部可能是被截断的 ZIP（缺中央目录），别因为解压器报错就判"文件坏了"，
改用按局部头切割。

### CRY-11 · WinZip AES 为什么 hashcat 破完还得自己解

ZipCrypto 是一个 12 字节弱流密码，口令对了就能边解边验，bkcrack 甚至能不爆破。
WinZip AES（method=99）完全是另一套：

```text
dk       = PBKDF2-HMAC-SHA1(pwd, salt, 1000, 2*keylen + 2)
enc_key  = dk[:keylen]          auth_key = dk[keylen:2*keylen]      pv = dk[2*keylen:]
密文      = AES-CTR(enc_key, counter=1 小端递增 128 位)
认证      = HMAC-SHA1(auth_key, 密文)[:10]  == 条目尾部 10 字节
```

所以 `hashcat -m 13600` 只能告诉你"这个口令对不对"，**文件内容仍要自己解密**。
反过来，自己实现时注意两点：CTR 计数器是**小端**且从 1 开始；认证只取 HMAC 前十字节。
**判断口令对错的正确姿势**：算 HMAC 比对，比"解出来看着像不像"可靠得多。
