**题面原文**：

> 附件里只有一行文本，找出 flag。

**初始判断**：第一反应"这就是 base64，解一层就完事"——错了，解出来是十六进制串，
这正是本题的唯一陷阱。

## 2. 一句话结论

Base64 解出十六进制串，再 hex 解码即得 flag；本质是**两级编码串联**，不是加密。

## 3. 解题路径（总览）

```text
附件 → [判型: Base64] → base64 解码 → 得到 hex 串 → hex 解码 → flag
                          ↓ 错误分支
                    [以为乱码 / 去跑 xor 爆破]
```

| 阶段 | 目标 | 用的东西 | 结果 |
|---|---|---|---|
| 1 | 判断是编码还是加密 | `ctf info`、熵值 | 纯文本，熵 4.13 |
| 2 | 解第一层 | `ctf dec` / Python | 56 个 hex 字符 |
| 3 | 解第二层 + 验证 | Python 标准库 | flag |

## 4. 关键步骤复盘

### 步骤 1 · 判型：编码还是加密

- **现象**：76 字节、单行、只有 `A-Za-z0-9+/=`、末尾 `=` 填充。
- **判断**：Base 家族编码。因为填充符和字符集是完全确定的指纹。
- **工具**：`ctf info` —— 先花 2 秒确认熵值，避免把编码当压缩/加密；备选 `file` 只能给"ASCII text"。
- **命令**：
```bash
ctf info artifacts/_build_chall.txt
```
- **输出（关键行）**：
```text
size      : 76 bytes (0.1 KiB)
entropy   : 4.133 bits/byte   (纯文本区间；压缩/加密通常 > 7.5)
magic     : unknown
```
- **解读**：熵不高 → 不是加密或压缩，是可以直接解开的编码。
- **知识点｜Base64 的 3→4 映射**：
  - 是什么：每 3 字节 24 bit 切成 4 个 6 bit 值，查 64 字符表；不足 3 字节用 `=` 补齐。
  - 为什么这里出现：出题人需要一个"看起来像乱码但一眼能认"的第一层。
  - 怎么认：长度是 4 的倍数、只有 64 个字符、末尾有 `=`。
  - 常见坑：base64url 用 `-``_` 代替 `+``/`；base32 只有 A-Z2-7。
- **下一步**：跑自动解码链。

### 步骤 2 · 用 BFS 解码链而不是猜

- **现象**：可能叠加了 base64/hex/rot13 的多层，手工排列组合容易漏。
- **判断**：编码级联。
- **工具**：`ctf dec` —— 按命中评分排序，一次给出所有组合；Python 手写 BFS 也可以，但没必要。
- **命令**：
```bash
ctf dec "$(cat artifacts/_build_chall.txt)"
```
- **输出（关键行）**：
```text
[1.00] input>base64:          '666c61677b623473655f31735f6e30745f656e637279707431306e7d'
[3.00] input>base64>hex:      'flag{b4se_1s_n0t_encrypt10n}'
```
- **解读**：评分 3.00 即命中；同层 rot13/rot47 分支是噪音，不用看。
- **知识点｜编码级联的识别**：解完一层后如果结果**仍满足某种编码的严格特征**
  （全 hex、全 base64 字符、偶数长度），就说明还有一层。反之出现 `{``}` 和可读单词就该停。
- **下一步**：手工复算，确认不是工具误报。

### 步骤 3 · 手工复算 + 闭环验证

- **现象**：工具命中也可能是巧合（尤其短串）。
- **判断**：验证闭环（MISC-03）。
- **工具**：Python 标准库，零依赖，任何机器能跑。
- **命令**：
```bash
python -c "import base64;h=base64.b64decode(open('artifacts/_build_chall.txt').read()).decode();print(bytes.fromhex(h).decode())"
```
- **输出**：
```text
flag{b4se_1s_n0t_encrypt10n}
```
- **解读**：与工具结果一致，格式符合 `flag{...}` → 正确。
- **知识点｜`bytes.fromhex` 的约束**：输入必须偶数长度且只含 hex 字符；
  报 `ValueError: non-hexadecimal number found` 就说明上一层解得不对。
- **下一步**：写 flag.txt 与本文档。

## 5. 工具与用法清单

| 工具 | 用在哪一步 | 关键参数 | 为什么选它而不是替代品 |
|---|---|---|---|
| `ctf info` | 判型 | — | 一屏给出哈希/熵/结构/flag 正则，比 `file` 信息多 |
| `ctf dec` | 解级联 | 直接传字符串 | 自带 BFS + 评分；CyberChef 要手动搭流水线 |
| Python | 验证 | `base64`/`bytes.fromhex` | 零依赖、可复制到任何环境 |

## 6. 知识点地图

| ID | 知识点 | 本题怎么用到 | 一句话原理 |
|---|---|---|---|
| ENC-01 | Base 家族 | 第一层解码 | 3 字节 → 4 个 6 bit 字符 |
| ENC-02 | 编码级联 | 解出 hex 后继续解 | 一层解完仍有编码特征就还没到底 |
| ENC-03 | 进制转换 | 第二层 hex→bytes | 每两个 hex 字符是一个字节 |
| MISC-04 | 编码 vs 加密 | 一开始就排除 xor | 编码无需密钥可逆，加密需要 |

**展开讲一个｜ENC-03 十六进制为什么是"两个字符一字节"**

十六进制的每一位能表示 16 种状态（4 bit），两个字符正好 8 bit = 1 字节。
所以 hex 串长度必为偶数；转回字节时是"两位一组"取值，而不是整串当一个数字。
这也解释了为什么 `1234` 可以被读成 `0x12 0x34`（两字节）或 `0x1234`（一个数）——
上下文（这里是文本）决定了它必须是两字节一组。

## 7. 卡壳与弯路

| 卡在哪 | 当时的错误假设 | 为什么错 | 怎么跳出来 |
|---|---|---|---|
| 起手跑了 xor 爆破 | 以为乱码是异或 | 熵 4.13 且字符集规整，明显是编码 | 回头看字符集与填充符 |
| 第一层解出 `666c...` 时以为还需要爆破 | 没认出这是 hex | 56 个字符、只有 0-9a-f、偶数长度 | 记住 ENC-03 的特征 |

**耗时分布**：判型 1 分钟 / 破局 2 分钟 / 验证 2 分钟。

## 8. 可复用脚本

`scripts/verify_b64_hex.py`（示例，可直接复用于同类题）：

```python
import base64, sys
raw = open(sys.argv[1]).read().strip()

```

## 9. 同类题迁移

### 9.1 30 秒识别

- 长度 4 的倍数 + 只有 `A-Za-z0-9+/=` → 直接 base64。
- 解出来"只有 0-9a-f 且偶数长度" → 立刻 hex，不要怀疑。
- 熵 < 6.5 的单文件题 → 基本是编码/格式题，不是密码题。

### 9.2 换变体会怎么改打法

- 换成 base32：长度是 8 的倍数、只有 `A-Z2-7=` → 用 `base64.b32decode`。
- 换成三层套娃：交给 `ctf dec` 的 BFS，别手算。
- 换成"解出来是一张图片"：把 hex 写回二进制，再按图片题流程走。

### 9.3 下次的第一条命令

```bash
ctf dec "$(cat artifacts/附件名)"
```
